# Skills and the agent kit

Every DocWiki release ships an **agent kit**: the files and tools that let any agent use the wiki
correctly, whether it runs in Microsoft Foundry, in your editor or in a terminal, online or from a
folder. The kit is generated by code from reviewed templates and validated catalog values; no part
of it is written by a model from document text.

## What is in the kit

| Item | Where | For |
|---|---|---|
| `AGENTS.md` | `wiki/AGENTS.md` | The agent guide: coverage, page types and frontmatter, navigation strategy, citation rules, contradictions and supersession, skills, MCP tools, and the rule that documents are data |
| `llms.txt` | `wiki/llms.txt` | A compact, [llmstxt.org](https://llmstxt.org/)-style index of the most useful pages |
| `catalog.json` | release root and `wiki/catalog.json` | Every page with its metadata and typed edges (`mentions`, `supersedes`, `cites`, `related`, `topic-of`) |
| `search.db` | release root | SQLite FTS5 over page sections and raw extracted blocks, expanded with glossary synonyms |
| Agent Skills | `wiki/.agents/skills`, `wiki/.claude/skills`, `wiki/.github/skills` | Reusable procedures: how to navigate, cite, research and maintain this wiki |
| MCP tools | `docwiki-mcp` | The same capabilities as tools, including `list_skills` and `get_skill` |

## Core skills

Four skills ship with every wiki, rendered from [`skills/templates/`](../skills/templates):

| Skill | What it teaches |
|---|---|
| `wiki-navigator` | Find information: home page, topic, entity and source indexes, glossary and log, with the MCP tools or plain file reads |
| `cite-sources` | Cite correctly: footnote targets, evidence sidecars, provenance badges, quotes kept in their original language |
| `deep-research` | A multi-step research protocol with bounded tool calls, contradiction and supersession handling and a cited report |
| `wiki-maintainer` | Maintain the wiki: adding and withdrawing sources, quality reports and run receipts, proposals, log entries |

## Domain skills

A domain pack may add at most three skills, each with an evaluation task in the golden set:

| Pack | Skill | Use it to |
|---|---|---|
| `wind-om` | `troubleshoot-alarm` | Investigate a turbine alarm or unexpected stop: alarm code, OEM guidance, past occurrences in the SCADA log, incidents, work orders, spare parts |
| `wind-om` | `prepare-maintenance-task` | Prepare a maintenance job: current procedure revision, parts and quantities, tools, torque values, isolation steps, applicable bulletins, stock |
| `wind-om` | `audit-readiness` | Check compliance readiness: permit conditions, procedures, audit findings, the records that prove compliance and the gaps |
| `it-runbooks` | `respond-to-alert` | Handle a monitoring alert: the service runbook, severity, first checks, escalation, related postmortems |

## One source, three projections

Agent clients look for skills in different folders, so DocWiki writes the **same bytes** to three
places in every wiki:

| Folder | Read by |
|---|---|
| `.agents/skills/<skill>/SKILL.md` | The canonical projection, the cross-client convention (Codex, GitHub Copilot) |
| `.claude/skills/<skill>/SKILL.md` | Claude Code |
| `.github/skills/<skill>/SKILL.md` | GitHub Copilot |

Gate G14 blocks a release unless the projections are byte-identical, the core skills are present,
no extra files sit in the skill folders, and every `SKILL.md` respects the limits: frontmatter
`name` in kebab-case (at most 64 characters, equal to its folder) and `description` (at most
1,024 characters), body at most 5,000 words.

Clients discover these folders when the **wiki folder itself** is the project they open. From
anywhere else, including from the repository root and from Foundry, the same skills are served
by the MCP tools `list_skills` and `get_skill`. See [local agents](local-agents.md).

## The template-only rule

Skills are instructions that agents follow. If skills were written by a model from document
content, one malicious document could plant persistent instructions in every agent that ever
reads the wiki. DocWiki therefore renders skills **only from reviewed templates**
([ADR 0005](adr/0005-skills-from-templates-only.md)):

- Templates are Jinja2 files reviewed like code: the core templates in `skills/templates/` and at
  most three per domain pack in `domains/<pack>/skills/<skill>/SKILL.md.j2`.
- Rendering uses a sandboxed environment with `StrictUndefined`: an unknown variable fails the
  build instead of rendering empty.
- The variables come only from validated catalog values and the domain pack (wiki title, counts,
  topic titles of the pack, entity types, fixed paths), never from document text. Every printed
  string is escaped for Markdown unless it is a validated path or identifier.
- Every rendered file is checked: frontmatter and size limits, Markdown safety (no raw HTML or
  external links) and the absence of injection canaries. The sample corpus plants a canary in an
  e-mail; gate G08 fails the release if it reaches `AGENTS.md`, a skill, an index, evidence or the
  site.

The cost of this rule is deliberate: skills cannot "learn" procedures from your documents. A
skill tells the agent **how to find and cite** a procedure in the wiki; the procedure itself
stays in the evidence, where it is cited and verified.

## Writing a domain skill

1. Create `domains/<pack>/skills/<skill>/SKILL.md.j2`. The frontmatter `name` stays literal and
   equal to the folder name; the rendered `description` must stay under 1,024 characters.
2. Use only these variables (all values are relative paths or validated strings):

   | Variable | Example |
   |---|---|
   | `wiki_title` | `Quellmoor Ridge O&M wiki` |
   | `paths.index`, `paths.glossary`, `paths.log` | `index.md`, `glossary.md`, `log.md` |
   | `paths.sources_index`, `paths.entities_index`, `paths.topics_index` | `sources/index.md`, … |
   | `topics` | list of `{slug, title, path}` for the topic pages present in the release |
   | `entity_types` | list of `{key, title, path}` for the entity types with at least one page |

3. Make loops render correctly when the lists are empty (`{% else %}` branches).
4. Add a golden-set task for the skill (category `skill`).

An extract of the `it-runbooks` template:

```jinja
---
name: respond-to-alert
description: Respond to a monitoring alert with {{ wiki_title }}. Finds the runbook of the alerting service, its severity, first checks, actions and escalation path, and related postmortems, all with citations. Use when an on-call engineer receives an alert or a user asks how to handle one.
---

# Respond to an alert

Use this skill with **{{ wiki_title }}**. Cite every step; never improvise commands.

## Steps

1. Read `{{ paths.index }}` and find the service of the alert in the entity indexes:
{%- for entity_type in entity_types %}
   - [{{ entity_type.title }}]({{ entity_type.path }})
{%- else %}
   - (no entity pages in this release - use full-text search)
{%- endfor %}
```

The core templates additionally receive counts, the pack's languages, the resolution order, the
MCP tool lists and the tool-call budget.

## Foundry and skills

The Foundry agents read skills on demand through `get_skill`. The infrastructure has an opt-in
flag for Foundry's skills preview (`DOCWIKI_ENABLE_FOUNDRY_SKILLS_PREVIEW`, default `false`); in
this version it is only recorded in the environment, and the MCP tools remain the way Foundry
agents read skills.
